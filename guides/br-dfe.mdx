## Introduction

Brazil has a variety of electronic tax documents that must be issued in different cases for various tax purposes. These include service invoices (NFS-e), product invoices (NF-e), and consumer invoices (NFC-e). Each document type is subject to variations from state to state and municipality to municipality, with each jurisdiction applying its own rules, formats, and APIs for issuing fiscal documents.

Invopop's **Documentos Fiscais Eletrônicos** app provides a unified way to issue fiscal documents across all Brazilian states and over 2000 municipalities using GOBL. You can find [the full list of supported municipalities here](https://tecnospeed.com.br/plugdfe/nfse/#homologacao).

This page holds what every document type shares: which document to issue, how it is checked, the environments, and the workflows. Each document type then has its own guide.

For onboarding suppliers, see the companion guide: [DF-e supplier registration](/guides/br-dfe-supplier).

## Which document for which sale

| Document | Use it for | Authority | GOBL |
|---|---|---|---|
| **NF-e**, model 55 | Goods sold to a business. Goods sold online or delivered to another state. Returns of goods | SEFAZ, the tax department of the issuer's state | [`br-nfe-v4`](https://docs.gobl.org/addons/br-nfe-v4) add-on |
| **NFC-e**, model 65 | Goods sold to a final consumer, in person or with home delivery in the same state | SEFAZ of the issuer's state | [`br-nfe-v4`](https://docs.gobl.org/addons/br-nfe-v4) add-on with the `simplified` tag |
| **NFS-e** | Services | The municipality of the issuer | [`br-nfse-v1`](https://docs.gobl.org/addons/br-nfse-v1) add-on |

An NFC-e only takes the in-person or home delivery presence codes ([`GOBL-BR-NFE-BILL-INVOICE-28`](https://docs.gobl.org/addons/br-nfe-v4#validation-rules)). Any other consumer sale of goods is an NF-e.

## How documents are checked

Each document goes through three checks, in this order:

| Step | Who checks | When it fails | Runs in sandbox |
|---|---|---|---|
| 1. Upload the entry | GOBL, with the add-on rules | The upload returns HTTP 422 with a `GOBL-BR-…` code | Yes |
| 2. Run the issue workflow | Invopop and its partner PlugNotas build the XML and sign it with the supplier's A1 certificate | The job fails | No, the sandbox returns mock files |
| 3. Authorization | SEFAZ for NF-e and NFC-e. The municipality for NFS-e | The job fails with the authority's rejection | No |

⚠️ A document that passes in the sandbox can still be rejected in homologação. GOBL doesn't run every authority rule. The [NFC-e guide](/guides/br-dfe-nfce#sefaz-checks-not-run-by-gobl) lists the SEFAZ checks to cover before you go live.

## Environments

| - | Sandbox | Live: homologação | Live: produção |
|---|---|---|---|
| **Workspace** | Sandbox | Live | Live |
| **Responses** | Simulated/mocked | From the tax authority's test environment | From the tax authority |
| **PDF & XML** | Always the same mock-up files attached to silo entry | Actual XML and PDF, no fiscal validity | Actual XML sent to tax authority and actual generated PDF attached |
| **Chosen** | Always simulation mode | When the supplier is registered | When the supplier is registered |

<Warning>
In live workspaces, documents are sent to the environment — homologation or production — that the supplier is currently registered in. Documents sent to homologation are processed by the tax authority's test environment and have no fiscal validity. See [Switch between environments](/guides/br-dfe-supplier#switch-between-environments) for how to check and change a supplier's environment.
</Warning>

## Running

As usual, the recommended approach for running jobs is to perform two steps; first upload the document to the [silo](/api-ref/silo/entries/create-an-entry-put), second [create a job](/api-ref/transform/jobs/create-a-job-put).

All operations can be performed manually via the Invopop Console, or programmatically via the API. The process is essentially the same in both cases. The example documents to upload are in each document type's guide.

### Cancel arguments

Run the cancel workflow of the document type over the silo entry you want to cancel. On success, the entry is set to `Void`.

The cancel actions accept optional parameters that control the cancellation request. They can be set as a default on the workflow step (via the step's configuration page in the Console) or overridden per job by passing them as arguments when [creating the job via the API](/api-ref/transform/jobs/create-a-job-put).

| Parameter | Job argument | Applies to | Notes |
|---|---|---|---|
| Cancellation reason | `nfe-br-cancel-reason` | NFS-e, NF-e, and NFC-e | Free-text reason for the cancellation. For NF-e and NFC-e, must be at least 15 characters if provided. Defaults to the system default when omitted. |
| Cancellation code | `nfe-br-cancel-code` | NFS-e only | Municipality-specific cancellation code, for example `9` for "Outros" in the National NFS-e system. Defaults to the system default when omitted. |

Job arguments take precedence over the step configuration. To pass them when creating a job via the API:

```json
{
  "workflow_id": "...",
  "silo_entry_id": "...",
  "args": {
    "nfe-br-cancel-reason": "Cancelamento a pedido do Prestador",
    "nfe-br-cancel-code": "9"
  }
}
```
